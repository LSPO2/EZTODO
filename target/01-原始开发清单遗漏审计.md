# 原始开发清单遗漏审计

审计日期：2026-07-24  
基线：根目录 `PC端AI_Todo开发任务清单.md`  
辅助证据：`docs/acceptance/requirements-matrix.md`、`docs/acceptance/*-evidence.md`、当前源码与自动化命令

## 1. 结论

原始清单包含 **388 个 P0 条目**。当前需求矩阵的 388 条明细逐条统计结果为：

| 状态 | 数量 |
|---|---:|
| 已实现 | 128 |
| 开发中 | 132 |
| 待开发 | 128 |
| 已验证 | 0 |

因此，项目已经具备较多本地任务基础能力，但仍属于“开发中”，不能按 PC MVP 发布。

矩阵顶部摘要写的是“待开发 78、开发中 82、已实现 228”，与同一文件的 388 条明细不一致。现有 `verify-matrix.js` 只证明 388 个 P0 ID 没有漏行，没有校验状态汇总，所以“矩阵覆盖通过”不能等价为“需求完成”。

根清单 Definition of Done 实际有 **12 条**（867～878 行），目前没有任何一条具备完整的自动化加真机验收证据。旧基线文档将其写成 11 条，也需要更正。

## 2. 影响发布的主要遗漏

### P0-A：验收和证据体系

- 需求矩阵没有从明细自动生成汇总，已经出现明显漂移。
- “实现文件存在”“组件能渲染”“单元测试通过”和“真机功能通过”仍混在部分旧记录里。
- Windows/Tauri 验收没有形成可复跑的证据包：SQLite 文件路径与重启持久化、托盘、通知点击、睡眠恢复、全局快捷键、窗口恢复、DPI、多屏。
- DoD 12 条没有逐条关联命令、测试、截图/日志、负责人和验收日期。

建议：先修复矩阵生成/校验脚本，再继续提升状态；没有证据的条目最多记为“已实现”。

### P0-B：账号、设备和同步

- M3 的登录、刷新/撤销、设备注册、多设备增量同步、幂等和冲突策略仍大面积处于待开发或开发中。
- 当前前端主入口没有形成完整登录与服务器配置闭环。
- 两设备不重复、离线队列恢复、墓碑传播和同步失败不丢数据尚未达到 DoD 证据要求。

### P0-C：时间、重复与提醒真机链路

- 重复规则和提醒模块已有较多实现/测试，但任务创建、修改、完成、删除与提醒调度的全生命周期仍需统一端到端验证。
- 睡眠跨过提醒时间、系统时区变化、安静时段、通知操作按钮、托盘隐藏后继续提醒仍需 Windows 真机证据。
- 月末、闰年和 DST 的库级测试不能替代真实系统时钟/时区验收。

### P0-D：AI 创建闭环

本轮之前的主入口存在三个实质问题：

1. 请求原后端接口时没有认证令牌，真实请求通常会得到 401。
2. 后端返回 `scheduled_date` 等 snake_case 字段，前端按 camelCase 读取，日期会丢失。
3. 请求失败后静默使用关键词规则，看起来像“AI 成功”，错误无法被用户识别。

本轮已新增 BYOK 设置与 OpenAI 兼容调用链，修复了上述伪接线问题，但仍有以下缺口：

- 未使用用户真实 API Key 做真机连接验收。
- 多任务/父子树当前按顺序写入，不是单事务；中途失败可能形成部分创建。
- AI 的提醒、重复、项目、标签建议尚未完整落库。
- `ai_captures` 缺少正式 Repository/Service 写入和隐私保留策略。
- API Key 目前仅会话内存保存；重启后需重填。要提供“记住密钥”，必须接入 Windows 凭据管理器。

### P0-E：安全需求冲突

原清单 466、570 行要求“客户端不直接携带大模型 API 密钥、密钥只保存在服务端环境变量”。用户新增的 BYOK 目标与此基线冲突。

本轮采用的最小风险策略是：

- Key 不写入 SQLite、localStorage、设置表或日志；
- 仅保存在当前前端进程内存，并通过 Tauri 原生 HTTPS 请求发送；
- 禁止远程 HTTP，只有 localhost/127.0.0.1/::1 可用 HTTP；
- 禁止 HTTP 重定向，避免 Authorization 被转发到其他站点。

这仍应被记录为“产品规则变更/可选 BYOK 模式”，不能把原有 server-only 条目直接标记为完成。长期建议保留两种模式：默认服务端代理，BYOK 作为明确提示风险的可选模式。

### P0-F：测试、发布和恢复演练

- M6 仍是待开发最集中的阶段，缺少完整集成测试、E2E、Windows 兼容和安装/升级/卸载证据。
- 客户端数据库备份恢复、服务端 PostgreSQL 备份恢复未形成双向演练记录。
- 自动更新、签名、回滚和数据库迁移失败保护未达到发布条件。

## 3. 代码层可改进点

| 问题 | 当前影响 | 建议 |
|---|---|---|
| `App.tsx` 超过 1000 行，大量内联样式和业务流程 | 修改风险高、组件测试困难 | 拆成路由/页面、hooks、服务和设计 token |
| `components/ai` 存在另一套未接入且有乱码的 AI 组件 | 重复逻辑、未来误用 | 统一为一个 AI 流程并删除/迁移旧组件 |
| 约 70 个 ESLint warning | `any` 与未使用变量掩盖类型问题 | 新代码零 warning，按模块逐步清零 |
| 主入口直接编排多步业务写入 | AI 父子树无法保证原子性 | 新建 `AICaptureService`，Repository 单事务提交 |
| API/模型响应类型散落 | 前后端字段漂移 | 共享 Schema 并生成/校验客户端类型 |
| 浏览器演示与 Tauri 行为差异 | 浏览器测试可能误判真机可用 | 为原生命令提供契约测试和 Tauri smoke test |
| 中文旧组件/文档曾有 mojibake | UI 可读性和维护性受损 | 全仓 UTF-8 检查进入 CI |

## 4. 审计边界

本审计确认了源码、测试、构建和矩阵明细；没有使用真实 AI Key、两台设备、Windows 睡眠/通知或安装包完成真机验收。因此文中没有把这些能力标记为“已验收”。
