# EZTODO 改进方案 v2：Claude Code + MiMo 严谨实施版

> 文档版本：v2.0  
> 编制日期：2026-07-22  
> 适用对象：使用 Claude Code 搭配 MiMo 模型持续开发 EZTODO 的开发者  
> 总原则：先守住架构边界和数据安全，再增加功能；“能看到页面”不等于“功能完成”。

---

## 0. 执行摘要

当前项目的主要风险不是缺少代码文件，而是**运行入口、数据源、模块实现和验收证据彼此脱节**。已经发生过一次典型回归：P0-1 曾将入口收敛到 `AppLayout -> Store -> Repository`，后续 P0-2 的 UI 修改又把 `App.tsx` 改回直接读写 `localStorage` 的单体页面。

因此，v2 将开发工作拆成两类：

1. **架构性任务**：改变数据链路、协议、迁移、同步、权限。必须小步实施、单独评审、先补测试后接 UI。
2. **功能性任务**：视图、编辑器、父子任务、筛选、回收站等。只能调用既有 Store/Use Case，不能为了“页面可用”绕过 Repository 或自行持久化。

本方案的目标是建立唯一且可验证的生产链路：

```text
React 组件
  -> Zustand Store（状态与命令）
  -> Use Case / Service（业务规则、事务边界）
  -> Repository（数据访问接口）
  -> Tauri SQLite（客户端离线真源）
  -> sync_outbox（同事务写入）
  -> Sync Client（幂等推送 / 增量拉取）
  -> FastAPI（认证、校验、冲突处理）
  -> PostgreSQL（服务端实体、事件与游标）
```

生产链路中的任何组件都不得直接读写 `localStorage`、拼接 SQL、模拟 AI 响应或将同步失败视为本地写入失败。

### 1.3 完成状态的严格定义

每条需求只能处于以下之一：

| 状态 | 含义 | 最低证据 |
|---|---|---|
| 待开发 | 未开始，或只有想法/界面草图 | 无 |

**禁止规则**：页面能显示、单测通过、或存在同名模块，均不能将状态从“开发中”提升为“已验证”。

## 2. Claude Code + MiMo 的开发协议

MiMo 适合快速生成实现，但对跨文件架构约束、未提交改动保护和“看似可用的演示逻辑”需要更明确的提示。本节是每次调用 Claude Code 前必须遵守的协议。

### 2.1 每次任务的输入模板

向 Claude Code 下达实现任务时，必须包含以下字段；不完整时先让它补计划，不直接编码。

```text
任务 ID：P0-1-xxx
目标：一句话描述用户可观察结果
允许修改：明确文件或目录白名单
禁止修改：明确保护文件、协议、迁移、未提交 WIP
架构约束：组件 -> Store -> Service -> Repository -> SQLite；禁止 localStorage 生产写入
数据约束：UUIDv7、UTC/时区、软删除、outbox 同事务
非目标：本任务不处理哪些功能
验收命令：lint / test / build / pytest / 指定集成测试
验收场景：给出输入、操作、预期数据库状态、预期 UI 状态
提交要求：单一逻辑提交；提交前 git diff --check
```

推荐实施提示词：

```text
请先只读检查 git status、相关接口、调用方和现有测试，输出 5 步以内实施计划。
未经确认不要改动白名单外的文件，不要覆盖当前未提交内容。
生产逻辑不得直接访问 localStorage；不得用 mock、setTimeout、占位 SQL 或 TODO 替代实现。
完成后运行指定验收命令，列出通过/失败项、未覆盖风险和 git diff --stat。
```

### 2.2 每次任务的硬性禁止项

以下行为出现任意一项，任务视为不通过，必须回退到可恢复检查点并重做：

1. 为方便演示而在生产 `App.tsx`、组件或 Store 中直接读写 `localStorage`。
2. 为让 UI “能跑”而绕过 Store、Repository、同步 outbox 或服务端校验。
3. 使用 `Date.now()` 作为业务实体 ID；使用 UUIDv4 代替已规定的 UUIDv7。
4. 在 SQL、同步、API 或 AI 逻辑中留下 `...`、`TODO`、空函数、固定成功响应或无条件 catch 后继续运行。
5. 将物理删除伪装为回收站；将内存数组更新伪装为持久化成功。
6. 改动数据库 schema、共享协议或删除语义却不新增 migration、契约测试和回滚说明。
7. 大范围重写 `App.tsx`、`package-lock.json`、迁移文件或部署文件，但没有明确原因和差异审查。
8. 依赖测试通过就声称 UI、Tauri、双设备同步或安装包已经验证。

### 2.3 每次任务结束的自检清单

Claude Code 每次完成后必须按以下格式输出；开发者只在全部满足时合并：

```text
1. 修改文件：逐个说明目的。
2. 架构检查：是否出现 direct localStorage / direct SQL / mock 主路径？结果。
3. 数据检查：ID、事务、软删除、outbox、迁移是否受影响？结果。
4. 测试命令及退出码：逐项列出。
5. 未覆盖场景：明确列出，不得写“无”。
6. Git 检查：git diff --check 与 git status --short 输出摘要。
7. 建议提交信息：符合 Conventional Commits，且只覆盖本任务。
```

### 2.4 独立复核提示词

不要让同一次实现会话自行宣布“完成”。每完成一个 P0 小任务，使用一个新的只读 Claude Code 会话复核：

```text
只读审查当前分支的任务 <任务 ID>。
按目标、架构边界、数据安全、失败路径、测试覆盖、与上一阶段的回归风险六个维度检查。
重点查找：direct localStorage、UUID 非 v7、未事务写 outbox、物理删除、空函数、占位 SQL、未接线组件、未提交改动覆盖。
不要修改文件。输出通过/不通过及精确文件和行号。
```

## 3. 目标架构与不可变边界

### 3.1 客户端分层

| 层级 | 允许职责 | 禁止职责 |
|---|---|---|
| Component | 渲染、表单输入、触发 Store 命令、显示加载/错误 | 数据库访问、同步、AI 解析、领域规则 |
| Store | UI 状态、调用 Use Case、将结果投影到界面 | SQL、localStorage、跨实体事务 |
| Use Case / Service | 父子联动、批量撤销、业务校验、事务编排 | React 状态、DOM 操作 |
| Repository | 读写实体、参数化 SQL、映射模型 | UI 判断、网络请求、硬编码视图样式 |
| Database Adapter | Tauri SQLite 连接、迁移、事务、备份 | 业务规则、浏览器自动降级 |
| Sync Client | outbox 推送、游标拉取、幂等重试、冲突状态 | 绕过 Repository 修改业务表 |

### 3.2 生产与演示环境隔离

必须提供明确的运行模式，而不是在 Tauri 失败时静默回退：

```text
production / tauri：只允许 Tauri SQLite；连接或迁移失败 -> 停止写入并提示备份恢复。
test：可使用内存/临时 SQLite；每个测试隔离数据库。
demo-browser：可使用浏览器适配器；页面显式标“演示模式，数据不用于生产”。
```

`repositories/index.ts` 必须根据显式 composition root 注入实现，不能永久导出 BrowserRepository。推荐接口：

```ts
export interface TaskRepository { /* 明确的领域方法 */ }

export function createRepositories(deps: { db: SqliteDatabase }): Repositories
```

应用启动时创建 `TauriSqliteDatabase` 并注入 Store/Use Case；测试时注入测试数据库；浏览器 demo 在独立入口显式注入 BrowserRepository。

### 3.3 数据一致性规定

1. 所有客户端实体使用 UUIDv7。推荐使用已安装 `uuid` 包的 v7 API 或可靠的 UUIDv7 库；禁止时间戳字符串和 UUIDv4。
2. 任务写操作的最低原子单元：更新任务/相关子任务 + 写 task event + 写 sync_outbox。任一步失败必须回滚。
3. `operation_id` 与实体 ID 分离；同一操作重试必须复用同一 `operation_id`。
4. 所有删除先写 `deleted_at` tombstone；物理清理由专用后台任务执行，前提是墓碑已同步且过期。
5. 客户端 migration 只能追加，升级前备份，失败后禁止继续写入。服务端使用 Alembic revision，禁止生产使用 `create_all` 代替迁移。
6. 时间字段：`scheduled_date`、`scheduled_at`、`due_at`、`remind_at` 不得混用；精确时刻使用 UTC，全天任务用本地日期。

## 6. P0-1：SQLite 真源、Repository 与离线写入（重新完成标准）

### 目标

实现真正的离线优先数据层，不再将 BrowserRepository/localStorage 作为默认实现。

### 工作包 P0-1-A：组合与连接

1. 实现 `TauriSqliteTaskRepository`、`TauriSqliteProjectRepository`、`TauriSqliteTagRepository`，或让现有 SQL Repository 正确成为默认生产实现。
2. 在应用 composition root 注入 Tauri SQLite 实现；Store 只依赖接口，不依赖具体 Browser/Tauri 类。
3. 为每个环境提供明确依赖组装；浏览器 demo 必须独立于桌面生产入口。
4. 数据库启动执行 `foreign_keys=ON`、WAL、`busy_timeout`、迁移检查。
5. 增加启动失败状态：迁移失败时展示“停止写入、可导出/恢复”的错误页，不能继续生成零散 localStorage 数据。

### 工作包 P0-1-B：迁移与模型

客户端 schema 必须含有：

```text
tasks, projects, tags, task_tags, reminders, recurrence_rules,
task_events, sync_outbox, sync_state, settings, ai_captures
```

每个表的字段、索引、外键与 shared contracts 对齐。必须特别校验：

- `tasks.parent_id` 自引用外键；
- `deleted_at`、`revision`、`source`、`source_capture_id`；
- 状态与 source 枚举包含实际业务使用值；
- 常用查询索引：状态、日期、项目、更新时间、删除时间；
- migration 前备份、版本表、失败回滚。

### 工作包 P0-1-C：原子写入与 outbox

每个操作必须经过 Use Case，例如：

```text
CreateTaskUseCase
  BEGIN
  -> insert tasks
  -> insert task_events(created)
  -> insert sync_outbox(create, stable operation_id)
  COMMIT
```

更新、完成、删除、恢复、移动父级、批量操作均采用同样原则。Repository 内部不能在任务写入成功后、事务外再异步写 outbox。

### 工作包 P0-1-D：ID 和浏览器适配器

1. 所有任务、项目、标签、提醒、事件、outbox 使用 UUIDv7。
2. Browser adapter 若保留，必须支持正确查询/更新/事务语义，或者只提供有限 demo API；不能冒充 SQL 实现。
3. 不能通过“返回全部数据”“只更新时间”的伪 SQL 行为让测试虚假通过。

### P0-1 必测场景

| 场景 | 操作 | 预期 |
|---|---|---|
| 离线创建 | 断网新建任务 | SQLite 有 task、event、outbox；UI 立即显示 |
| 重启 | 退出后重开 | 仍显示同一 UUIDv7 任务，无 demo 重置 |
| 写入失败 | 模拟 outbox 插入失败 | 任务、event、outbox 均不落库 |
| 迁移失败 | 模拟一条 migration 出错 | 业务写入停止，存在迁移前备份 |
| Tauri SQL 失败 | 模拟插件连接异常 | 生产模式不落到 localStorage |

### P0-1 退出条件

- 运行时只存在一个生产数据真源：Tauri SQLite。
- 所有本地写操作事务化并写 outbox。
- UUIDv7、软删除、迁移备份有自动化测试。
- 当前 `App.tsx` 不再出现 direct localStorage 或 `Date.now()` ID。

## 7. P0-2：本地 Todo 与父子任务（重新完成标准）

### 目标

在 P0-1 的真实数据链路上实现完整本地 Todo；UI 功能不得以数组或浏览器存储模拟。

### 工作包 P0-2-A：基础 CRUD 和视图

实现以下 Store/Use Case 命令，并由组件调用：

```text
createTask, updateTask, completeTask, reopenTask, softDeleteTask,
restoreTask, copyTask, moveTaskToProject, setTaskPriority,
addTagToTask, removeTagFromTask, reorderSiblingTasks
```

必须提供 Inbox、今天、未来 7 天、已逾期、无日期、已完成、回收站。视图定义只在 Query/Repository 层维护，组件不能再复制筛选逻辑。

### 工作包 P0-2-B：搜索、筛选、排序

1. 搜索标题和备注。
2. 筛选项目、标签、优先级、状态。
3. 排序计划时间、截止时间、创建时间、手动顺序。
4. 支持“仅父任务”和“展开全部子任务”。
5. UI 必须显示当前筛选条件，并支持一键清除。
6. 为 10,000 任务固定数据集建立性能测试，记录机器、数据分布、P95 查询与渲染时间。

### 工作包 P0-2-C：批量操作与撤销

批量完成、恢复、删除、移动项目、添加/移除标签、修改优先级必须：

- 在一个业务事务中执行；
- 产生一个 `batch_id` 或等价撤销令牌；
- 向 outbox 记录全部实体变化；
- 显示可见撤销入口；
- 撤销操作本身也进入 outbox。

### 工作包 P0-2-D：父子任务规则

父子任务规则必须由 Use Case 统一实现，不得只在 UI click handler 中实现。

1. 最多 3 层；创建、缩进、移动时都做深度校验。
2. 禁止将任务移到自己的子孙节点下；使用递归查询或完整祖先链检查。
3. 子任务全部完成，自动完成父任务；联动的所有变更在同一事务和同一 outbox 批次。
4. 完成仍有未完成子任务的父任务时，弹窗必须明确提供：
   - 仅完成父任务；
   - 同时完成所有子任务；
   - 取消。
5. 重新打开父任务时，弹窗提供是否恢复已完成子任务。
6. 删除父任务时父子全部软删除；恢复父任务时完整恢复父子关系。
7. 子任务截止时间晚于父任务时给 warning，不阻断保存。

### P0-2 必测场景

| 类别 | 必测用例 |
|---|---|
| CRUD | 创建、编辑、复制、完成、重新打开、软删除、恢复 |
| 筛选 | 项目+标签+优先级组合筛选，清除筛选恢复完整结果 |
| 批量 | 批量完成后一次撤销；批量删除后一次恢复 |
| 层级 | 三层允许、四层拒绝、循环移动拒绝、缩进/提升正确 |
| 联动 | 最后一个子任务完成 -> 父自动完成；父完成三选项；父重开恢复选项 |
| 回收站 | 删除父任务 -> 所有子任务出现；恢复 -> 关系与状态正确 |
| 性能 | 10,000 条任务视图、搜索、筛选在目标阈值内 |

### P0-2 退出条件

- 每个 UI 操作最终调用 Store/Use Case/Repository，而不是在组件内部直接变更数组。
- 删除绝不物理 `filter` 移除；回收站可见并可恢复。
- 父子规则、批量撤销和 10,000 条性能都有测试与验收记录。
- P0-1 所有数据链路测试在 P0-2 合并后仍通过。

## 8. P0-3：提醒、重复任务与 Windows 外壳

### 目标

将已有的工具模块接入真实任务与 Tauri 生命周期。

### 实施规则

1. TaskDetail 必须通过 Reminder/Recurrence Use Case 编辑真实 SQLite 数据。
2. 时间修改、删除、恢复、重复实例生成时，旧提醒必须取消并重新调度。
3. 重复规则覆盖每日、工作日、周指定日、月指定日、年指定日、完成后 N 天、起止日期与跳过本次。
4. 月末、闰年、夏令时、时区变化、系统时间跳变必须测试。
5. 系统唤醒后扫描错过提醒；通知支持完成、稍后 10 分钟、1 小时、明天；点击定位任务。
6. Tauri 实现真实单实例、窗口状态保存、关闭隐藏到托盘、托盘菜单真实动作、快捷键真实动作。
7. 补齐 `src-tauri/icons` 资源，并在实际 Tauri 环境验证，而不是仅验证 Vite 页面。

### 退出条件

主窗口隐藏到托盘后，真实 SQLite 任务提醒仍可触发；睡眠/唤醒和时间变更不会重复或遗漏提醒。

## 9. P0-4：后端、认证、同步与安全部署

### 目标

从“同步操作日志示例”升级为可恢复、可幂等、可冲突处理的实体同步系统。

### 服务端数据与迁移

1. 建立 Task、Project、Tag、TaskTag、Reminder、RecurrenceRule、AICapture 等 SQLAlchemy 模型。
2. 所有生产 schema 修改通过 Alembic revision；建立 upgrade/downgrade 测试。
3. 禁止以 `Base.metadata.create_all()` 代替生产迁移。
4. 发布前自动备份数据库，迁移失败时可回滚 API 镜像和数据库。

### 认证与设备

1. 使用受控管理员初始化流程建立首用户；不开放公开注册。
2. Argon2id 密码，短期 Access Token，轮换 Refresh Token；刷新 Token 只保存哈希。
3. 客户端凭据使用系统安全存储；不得进入 localStorage、日志、任务数据库、普通设置文件。
4. 登录、AI、导入接口配置速率限制、请求体上限和失败审计。

### 同步协议

1. Push 幂等：相同 `operation_id` 返回先前结果，不重复修改实体。
2. Pull 增量：服务端版本/游标递增；分页、断点续传；删除以 tombstone 同步。
3. 服务端在一个事务内应用实体变化、写事件、推进游标。
4. 冲突策略固定：普通字段按服务端版本最后写入胜出；删除/修改保留可恢复副本；父子关系重验无环与深度；不可自动合并生成 conflict copy。
5. 客户端远端应用不得存在 `...` SQL、空 project/tag handler 或旁路写库。

### 部署红线

- PostgreSQL 不发布到公网；只位于内部 Docker network。
- 生产 Caddy 使用真实域名和 HTTPS；不能只监听 `:80`。
- `JWT_SECRET_KEY`、数据库密码、AI Key 不得有默认生产回退；检测占位值后拒绝生产启动。
- CORS 仅允许必要 origin/method/header。
- Healthcheck 使用实际可用工具，并用 `/ready` 验证数据库。

## 10. P0-5：真实 AI 建任务

### 目标

用“确定性规则 + Provider + 服务端硬校验 + 用户确认”取代本地关键词模拟。

### 规则

1. UI 通过已认证 API 请求 AI，禁止硬编码 `localhost` 和遗漏 Authorization。
2. 前后端使用同一契约；snake_case/camelCase 映射必须有契约测试。
3. 仅“解析出标题”不得判定为 high。high 需要字段合法、无关键不确定项、无 warning 且满足回归阈值。
4. 模型输出后强制校验：最多 20 任务、最多 3 层、标题长度、合法日期/时区/优先级/提醒/重复规则。
5. medium/low 必须显示可编辑确认卡；high 自动创建后必须提供一次性撤销。
6. 请求可取消；重复点击使用请求 ID 去重；失败保留原文。
7. 明确日期时间语料准确率目标至少 95%，明确重复规则至少 90%；提示词/Provider/解析规则变更均跑回归。
8. 日志只记录耗时、模型、Token、错误码、capture 状态；默认不记录敏感正文和密钥。

## 11. P0-6：回收站、导入导出、备份恢复

### 规则

1. 所有删除先进入回收站；显示即时撤销；30 天后才允许物理清理。
2. 恢复父任务时恢复子任务；永久删除二次确认，并确保 tombstone 已同步。
3. CSV 使用标准 parser，禁止 `split/join`；支持 UTF-8/UTF-8 BOM、字段映射、预览、错误报告、重复检测、批次取消和整批撤销。
4. 完整 JSON 包含任务、父子、项目、标签、提醒、重复规则、格式版本和创建时间。
5. 恢复前自动备份当前数据库；备份与恢复做完整性校验并显示影响范围。

## 13. 推荐提交与分支粒度

每个提交只完成一个可回归的最小闭环，建议：

```text
fix(p0-r0): restore composition root and remove direct production storage
feat(p0-0): complete requirement traceability and quality gates
feat(p0-1): inject tauri sqlite repositories into desktop runtime
feat(p0-1): make task write and outbox insertion atomic
test(p0-1): cover offline persistence and migration failure
feat(p0-2): add soft-delete and restore use cases
feat(p0-2): implement parent-child completion transaction
test(p0-2): cover hierarchy, cycle detection, and undo
```

禁止将“重构入口、改 schema、加 UI、改同步、更新文档”混在一个提交中。一个任务若需要跨层改变，应拆成“契约/迁移 -> Repository/Use Case -> Store/UI -> 测试 -> 文档”多个提交。

每次提交前固定执行：

```text
git diff --check
git diff --stat
git status --short
npm run lint
npm run test
npm run build
services/api/venv/Scripts/python.exe -m pytest tests -v
```

如果任务不影响后端或 Tauri，可说明跳过理由；不得静默跳过。

## 14. 最终 Definition of Done

EZTODO 只能在以下全部成立时标记为“PC MVP 已完成”：

1. 离线状态下可使用完整基础任务功能，重启后数据保持。
2. 每次本地写入经过 SQLite 事务并有同步 outbox；同步失败不丢数据。
3. 两设备同步不产生重复任务；冲突不会静默丢失内容。
4. 删除可撤销，可在 30 天内完整恢复父子任务。
5. 父子规则无循环、无越级、无半完成状态；重复任务在月末、闰年和时区变化下正确。
6. 主窗口隐藏到托盘后提醒仍有效，通知可完成/稍后并定位任务。
7. AI 经服务端严格校验，失败不丢原文，低置信需确认。
8. 用户可完整导出、导入和恢复数据；客户端与服务端恢复演练都有记录。
9. 所有 P0 均为“已验证”，所有 CI 与干净 Windows 安装验证通过。

在此之前，项目状态必须是“开发中 / 不可发布”。
